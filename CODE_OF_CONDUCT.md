# ELSHWORK Code of Conduct

## Purpose

ELSHWORK is built for developers, researchers, maintainers, contributors and technical communities.

We want collaboration inside the project and its public repositories to remain:

- professional;
- constructive;
- technically focused;
- respectful;
- safe for participation.

This Code of Conduct applies to public project spaces associated with ELSHWORK, including:

- GitHub Issues;
- Pull Requests;
- Discussions;
- code review;
- documentation contributions;
- community discussions;
- other official collaboration channels.

---

## Our standard

Participants are expected to:

- communicate respectfully;
- criticize ideas and code rather than people;
- provide useful technical context;
- assume good faith when reasonable;
- accept corrections professionally;
- respect privacy;
- avoid unnecessary hostility;
- keep discussions relevant;
- help maintain a productive environment.

Disagreement is normal.

Personal attacks are not.

---

## Constructive technical discussion

Good technical disagreement may look like:

> I do not think this implementation preserves the repository permission boundary because the authorization check happens only in the frontend.

or:

> This approach adds a duplicate domain model. Could we reuse the existing ResearchRevision structure instead?

This is encouraged.

Discussion should focus on:

- implementation;
- architecture;
- evidence;
- security;
- performance;
- maintainability;
- user experience.

---

## Unacceptable behavior

The following behavior is not acceptable in ELSHWORK project spaces:

- harassment;
- threats;
- intimidation;
- targeted insults;
- discriminatory abuse;
- deliberate humiliation;
- repeated personal attacks;
- doxxing;
- publishing private information without permission;
- sexual harassment;
- malicious impersonation;
- sustained disruption of technical discussion;
- spam;
- scams;
- intentional misinformation intended to harm users;
- attempts to pressure contributors into revealing secrets or credentials.

---

## Security-related behavior

Security discussion is welcome when handled responsibly.

Do not:

- publish active secrets;
- expose private repository contents;
- disclose personal user information;
- publicly release exploit details before maintainers have had reasonable time to investigate;
- use security research as justification for unnecessary access to user data.

Potential vulnerabilities should be handled according to:

```text
SECURITY.md
```

---

## Privacy

Respect the privacy of other participants.

Do not publish:

- private messages;
- private email addresses;
- access tokens;
- credentials;
- private repository content;
- personal information;

without authorization.

---

## Reviews

Code review should remain focused on the contribution.

Acceptable:

> This state transition can bypass the expected-result lock.

Not acceptable:

> You clearly have no idea how backend development works.

Review should improve the code, not discourage contributors.

---

## Research discussions

Research criticism is allowed and encouraged.

Participants may challenge:

- methodology;
- evidence;
- reproducibility;
- interpretation;
- results.

However, criticism should address the work rather than the personal characteristics of the researcher.

A failed reproduction is not misconduct by itself.

A disagreement with a result is not harassment.

---

## Reproducibility

ELSHWORK is designed to support independent verification.

Participants should not pressure reproducing users to:

- change honest negative findings;
- report a positive result;
- hide conflicting evidence;
- withdraw legitimate criticism.

A correctly performed negative reproduction is a valid contribution.

---

## Conflicts of interest

Participants should disclose relevant conflicts of interest when they materially affect:

- Research review;
- independent reproduction;
- Marketplace review;
- security decisions;
- governance.

Disclosure helps preserve trust.

---

## Marketplace discussions

Marketplace sellers and users must not use project spaces for:

- fraudulent claims;
- fake reviews;
- deceptive promotion;
- impersonation;
- manipulation of verification status.

Security and seller verification are platform trust mechanisms and should not be bypassed socially.

---

## Moderation

Maintainers and moderators may take action when behavior disrupts the project or creates safety risks.

Possible actions include:

- request for correction;
- warning;
- removal of content;
- temporary restriction;
- participation restriction;
- ban from project spaces.

Actions should be proportionate to the situation.

---

## Appeals

Where applicable, moderation decisions may be reviewed or appealed through available project or platform processes.

An appeal does not automatically remove the original moderation record.

---

## Good-faith mistakes

Not every mistake is misconduct.

A contributor may:

- misunderstand a rule;
- make a technical error;
- use unclear wording;
- accidentally create duplicate work.

When reasonable, correction and explanation should be preferred over escalation.

---

## Repeated behavior

Repeated harmful behavior after clear warnings may result in stronger moderation.

Intent, severity, impact and history may all be considered.

---

## Maintainer responsibilities

Maintainers should:

- apply rules consistently;
- avoid using moderation to suppress legitimate technical disagreement;
- protect user privacy;
- document serious moderation decisions where appropriate;
- avoid conflicts of interest;
- respect the same standards expected from contributors.

Maintainer status does not exempt anyone from this Code of Conduct.

---

## Scope

This Code of Conduct applies to official ELSHWORK project spaces.

Behavior outside those spaces may be considered when it directly threatens:

- project participants;
- project infrastructure;
- user safety;
- project integrity.

---

## Enforcement

Moderation or enforcement decisions may consider:

- severity;
- repetition;
- intent;
- impact;
- prior behavior;
- security implications.

ELSHWORK should avoid both extremes:

- ignoring harmful behavior;
- turning ordinary technical disagreement into misconduct.

---

## Principle

The goal of this Code of Conduct is not to eliminate disagreement.

The goal is to make disagreement productive.

---

Build seriously.

Review honestly.

Disagree professionally.
